# Changelog

All notable changes to `@cottagehop/here-be-dragons`.

The format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Unreleased

- **GPU frame pacing: one frame in flight (was two).** The splat sort's readback waits for every frame queued ahead of it on the GPU, so the queue's depth is the stall's length. Two frames deep was the right trade when a held tick showed nothing; with reprojection presenting the camera's motion on every held tick, the frames not drawn cost nothing visible and the stall halves. Measured interleaved on an Intel Iris: presented p95 32–39 → 20–21 ms, interval jitter (sd) 10–11 → 7 ms, frames over 50 ms 7 → 1–5, readback stall 7–9 → 4 ms mean, warped presents 170 → 194 per pan. The landing-time special case from the previous entry is now the general rule.

- **Splats: the loading hitches, found and removed.** A CPU profile and a per-GL-call trace of the load window showed where the main thread went while tiles arrived — not the splats (their textures: 8 ms for 22 MB) but (a) the ground imagery: `TextureLoader` uploads through the browser's conversion path cost 18–30 ms per 2048² image, 197 ms over a seven-tile load, two to four bunching into 72 ms frames — the imagery is now decoded to an `ImageBitmap` with every conversion off (flip done in the decode, bitmap closed with the texture): 52 ms for 101 MB; (b) one depth re-sort per landing, each blocking the main thread for a frame's worth of GPU queue — at REST every decoded tile and image now lands in the same frame (one regeneration, one sort for the batch; one per frame only while moving); (c) while tiles land or dissolve the map paces to ONE frame in flight, so a gesture that starts mid-landing waits behind one heavy frame, not two: worst frame 86 → 50–67 ms, and the pan's presented p95 44–45 → 29–33 ms; (d) motion-LoD lite twins no longer take a fetch/decode slot while any wanted tile is still in flight; (e) Spark's module import is kicked at map construction so it overlaps the map's own start-up. End to end on the demo (two runs): the first detail tile lands at 1.2–1.5 s from construction instead of 3.1 s, all detail by 1.5–1.7 s instead of 3.9 s; readback stalls during the load 412 → 158–252 ms. Left as is: Spark's one-time init (~175 ms of main thread) and three/Spark's own first-render work on a mapping change (a few 40–90 ms frames per load).

- **Splats: detail arrives faster.** Three changes, measured on the demo with a per-tile timeline (`probe_loadtime.mjs`: fetch start, bytes, decode, landing): (1) the detail tile under the view focus loads FIRST, before the cover window — it is what the user is looking at; (2) `maxInFlight` defaults to `4` (was `1`): Spark decodes in a pool of four workers, and with one load in flight every tile's fetch and decode ran strictly in series — the first detail tile started 700 ms after the first fetch and three detail tiles landed 380 ms apart; (3) the level dissolve (`levelFadeMs`) defaults to `350` ms, the motion system's base duration, instead of 450. Result: the focus detail tile lands ~280 ms after the first cover tile (was ~1 s), with no pan-smoothness cost from the parallel decodes (presented 52 fps / p95 ~50 ms in both arms). After a pan, the new tile is decoded before the glide ends and lands at the settle, as designed. Two limits in the trace are outside the map: the demo's Python tile server used to answer one request at a time (now threaded), and concurrent decodes slow each other on a 6-core machine (250–400 ms each vs ~200 alone).

- **Splats: a cover level under the detail window — `splats.cover` (default `true`).** The next coarser pyramid level's window is now always wanted: loaded FIRST (from the lite pyramid when one is configured) and kept resident outside the splat budget, so the whole view is satellite instead of an island of detail on the vector map. `maxSplats` buys detail tiles ranked from the view centre outward; each dissolves in over its parent's quadrant through the existing level-fade machinery, the parent's splats under a landed child leave the sort and draw (inactive), and a detail tile over a landed parent draws square (its rounded-union corners would open wedges). In MOTION, detail tiles other than the one under the view focus hide and their cover parent shows (coarse, and blurred by the miniature anyway); they dissolve back in from the centre at rest — without that, the cover's resident splats scaled Spark's generate and depth passes and a pan lost a quarter of its drawn frames. Zooming out hands over cleanly: the cover becomes the detail level, a new cover loads beneath, the old detail dissolves out (tested). Measured at the capped view on an Intel Iris (2 interleaved rounds): the whole frame is imagery at rest and mid-pan; the pan's drawn fps 44–50 → 36 and presented p95 25–32 → 42–45 ms, for showing the whole view instead of a third of it — the cover's coarse splats are large, so the density LOD keeps them (active splats p50 102k → 154k) while Spark's mapping in motion actually shrinks (540k → 482k). Off on the low tiers; `getSplatsStats()` reports `coverTiles` / `coverSplats`, the demo HUD shows `3t+4c`.

- **Fixed: in-flight tile loads were abandoned by level.** `updatePrefetch` dropped every pending load that was not at the active or prefetch level — with a second level in play it fetched, decoded and abandoned the cover tiles on every tick (9 requests a frame, nothing resident). It asks `levelsInPlay()` now.

- **Dynamic resolution no longer resizes the canvas.** The motion picture is rendered INTERNALLY at the cheaper ratio (`Composer.setRenderScale`: every target at canvas × scale, the final pass upscaling into the unchanged canvas) and Spark is told the scale through `focalAdjustment` so splat footprints stay right; the density LOD measures against the internal height. Reallocating the canvas's drawing buffer along with the targets had cost ~20 ms of main thread on the first moving tick of every gesture — the frame the user is waiting for — and again at every settle. Measured on an Intel Iris at the capped view, first presented frame after a gesture starts: 67–113 → 42–51 ms on a fresh page's first gesture, 43–56 → 25–30 ms after that; the first moving tick 37–47 → 19 ms (first gesture) and 20–30 → none (later ones). The last frame is also kept across the internal resize (`captureHeldFrame`) so reprojection shows the gesture's first ticks instead of nothing while the swap hold waits. `getPixelRatio()` still reports the effective rendering ratio.

- **Splats: the miniature look — `splats.miniature` (default `true`).** While satellite tiles are on screen the overlay drives the map's tilt-shift: on, with an imagery preset (`MINIATURE_IMAGERY_TILT_SHIFT`: the same shallow focus band on the point the camera looks at, saturation 1.15 / contrast 1.06 / vignette 0.18 instead of the vector map's 1.35 / 1.08 / 0.2 — the neutral grade has just taken the painterly saturation off the photographs, and the full grade would put it back as neon), eased in as the first tile lands and out when the last one goes. The lean map, which parked the blur while splats showed, makes way for it. Settings given to `setTiltShift({ … })` are honoured instead of the preset and survive the hand-back. Labels stay sharp above the blur, and the reprojected and dissolve presents carry the blur with the frame.

- **Tilt-shift blur at half resolution.** The two 13-tap blur passes now run on quarter the pixels and a full-resolution composite takes the sharp band from the full-res image and the blur from the half-res one (`configureBlur` / `configureComposite`; one uniforms object behind both materials). Measured with the splat overlay in a pan on an Intel Iris: the full-res blur cost 15–20 ms of presented p95 (30–40 vs 18–21 ms) and 10–17 drawn fps; at half resolution the miniature is free — presented 57–58 fps, p95 19–20 ms, the same as with it off. A blur at this radius looks smoother for it, not worse.

- **Splats: the camera is held at zoom 15 and a 45° tilt while the 3D imagery is on.** `maxCameraZoom` now defaults to `15` (was 16.5) and a new `maxCameraTilt` (default `45`, degrees from straight down; ≥ 89 = none) lays a tilt cap over the map's own tilt range the way the zoom cap sits over its zoom range: `MapCameraController.setMaxTiltCap` eases a steeper camera up to it over 600 ms, a tighter `setTiltRange` still wins underneath, and lifting the cap puts the range back exactly (unit-tested). Closer than zoom 15 the surfels read as blobs; steeper than 45° the view runs into the satellite layer's far field — many tiles, sub-pixel splats, the horizon — and out of the miniature look.

- **Reprojection on held ticks — `performance.reprojection` (default `true`).** While splat tiles are resident the frame is GPU-bound and some ticks draw nothing: GPU frame pacing holds one back when two frames are still unfinished, and the motion-LoD swap hold keeps the picture while the lite set sorts. Those ticks now present the last frame *warped to the current camera* instead of repeating it — VR's timewarp, for a map: each pixel's view ray is intersected with the ground plane and that point projected with the camera the frame was drawn with (`ReprojectPass`, one full-screen pass plus FXAA, nothing of the scene rendered). Exact for the ground; a 10 m roof 300 m away is ~0.2 px out for the one frame the warp shows; sky rays reproject by rotation; the strip the camera moved towards clamps to the frame's edge. Measured on an Intel Iris, 2 interleaved rounds: the **presented** interval's p95 32/30 → 19/19 ms with 11–14 warped presents per pan (the few held ticks were exactly the uneven ones), a busy second gesture's worst frame 101/119 → 57/104 ms and then a flat 16–17 ms. The reprojection and dissolve shaders are compiled at construction (`compileAsync`): on a fresh page the first warp had cost a gesture its first frame (341 ms). `getRenderStats().reprojected` counts warped presents; `false` repeats the last frame on held ticks, as before.

- **Splats: screen-space density LOD — `splats.densityLod` (default `2`, device px; `0` = off).** A game renderer's oldest economy: a constant number of samples per *pixel*, not per metre. Each splat's sampling spacing (twice its scale, for surfels authored at σ = ½ spacing) is projected to the screen from the tile's own camera position; where it falls under the target, only a hashed fraction is kept and the survivors grow to keep the surface covered, on the same hash and in the same shader node as motion thinning. Near splats are untouched; the far field of a tilted view — several surfels to a pixel, costing full price — is where it bites. Follows the drawing-buffer size, so the 1× motion picture thins harder than the 2× rest one. Measured on the CdA demo at a 62° tilt: at rest 28 % fewer splats drawn on the 2× buffer (mean pixel change 0.17/255, 0.08 % of pixels by more than 24) and 54 % fewer on 1× (0.67/255), neither distinguishable side by side; in a pan (already at vsync), frames over 50 ms 8/7 → 5/4, the sort's readback 22 → 17 ms, a busy second gesture's worst frame 189/315 → 98/135 ms, and the governor's motion thinning ends higher — detail moved from the far field to where the camera looks. `1.5` is the conservative setting (15 % / 0.06 on 2×).

- **Camera inertia is defined in seconds, not frames.** MapControls applies its damping factor once per `update()`, so a glide decelerated three times as much through a 50 ms frame as through a 17 ms one — the motion itself jittered with the frame time, and a fling travelled a different distance at 30 fps than at 60. `MapCameraController.update(dt)` now rescales the factor to the frame's length (`BASE_DAMPING` per 1/60 s, bounded at 100 ms), so the deceleration curve is the same at any frame rate, like a platform scroll; the sub-pixel glide stop and the motion-detail ramp measure their steps per reference frame to match.

- **Splats: detail comes back over the second half of a scroll or fling, not after it.** The map measures the camera's on-screen step every tick; an inertia glide slows by a fixed fraction a frame, so halfway through it in TIME is the geometric mean of the gesture's peak speed (for a drag: its release speed) and the stop speed (`core/motionDetail.ts`). From there the overlay swaps its lite meshes for the full ones — cross-faded, full in over the still-opaque lite set, then lite out, using Spark's per-mesh opacity — starting at the lite set's density, and raises the kept fraction to every splat exactly as the glide stops: detail, and frame cost, go up as the motion goes down. Newly kept splats fade in through a soft band above the threshold, and the rise is capped at what Spark's last landed depth sort already holds (sorts are detected by their start stamp), so they never arrive in batches at a sort. Full and lite meshes now have their own thinning uniforms, so the ramp never coarsens the lite set it is fading out. Ramp frames count as a transition for the governor. Measured on an Intel Iris, a released drag gliding 1.4 s: detail starts at ~0.6 s and completes at the stop (kept fraction 0.16 → 1.0 while the step falls 0.6 → 0.27 px); the lite → full swap, a visible step before (14 % of the post-release change in one frame), no longer stands out from the motion.

- **Detail no longer pops back after a gesture: a settle dissolve — `performance.settleFadeMs` (default 400 ms, `0` = snap).** When the picture sharpens at rest — dynamic resolution returning to full, the splat overlay leaving its motion LoD — the composer captures the last moving frame, keeps it on screen while the sharp picture gets ready behind it (≤ 700 ms), then cross-fades into it with an ease-in-out: one focus pull instead of a resolution pop followed by a detail pop, and a brief pause mid-gesture shows nothing at all. The fade owns the frame: its steps blend two textures (`Composer.present()`, new `DissolvePass`) without re-rendering the scene, and other render requests during it (tiles landing after the gesture, their reveal) wait the few hundred ms. Any camera motion cancels it. Measured on an Intel Iris by reading back a screen patch after every presented frame: the old snap delivered 19 % of the whole post-release change in ONE frame (a step of 14.9 / 255); the dissolve spreads it over 26 blend frames 15–20 ms apart, none above 0.96, and the frame after it changes by 0.02. `getRenderStats().dissolveFrames` counts blend-only frames. Off under `prefers-reduced-motion`.

- **The inertia glide ends once it is sub-pixel.** MapControls damps per frame and keeps creeping long after a drag visibly stops — measured 0.35 CSS px a frame 0.3 s after release, still 0.02 px at 1.3 s, with sporadic later steps — and every one of those invisible steps counted as camera motion: the splats stayed on their blurry motion LoD and low resolution, and the late steps flipped detail blurry → sharp → blurry at rest. `MapCameraController` now drops the rest of the glide once its next step is under 0.25 CSS px (never during a live gesture): the camera stops a few pixels short of where an invisible tail would have taken it, and the map actually reaches rest.

- **Splats: the governor's thinning steps ease while moving** (τ 120 ms) instead of jumping 70 % → 50 % → 35 % of the splats mid-gesture, one cheap regeneration a frame; the flip into motion and the return to rest still snap, covered by the swap hold and the settle dissolve.

- **Splats: motion thinning — `splats.motionThin` (default on), the governor's new first rung.** While the camera moves and frames run over `targetFrameMs`, keep only a hashed fraction of each tile's splats (0.7, then 0.5, then 0.35), the survivors grown by 1/√keep so the surface stays covered; every splat is back at rest. A dropped splat gets Spark's inactive flag, which its packer writes as zeros, so it leaves the depth sort and the instanced draw entirely (opacity 0 alone would still be sorted and drawn). The hash (PCG on the splat index) is stable and nested, so the picture does not shimmer between rungs. Only after the thinning ladder does the governor cut distant relief or evict tiles, and it recovers in the reverse order. Diagnosis first: during a pan the governor used to walk the distance ladder (no effect at this camera: every tile is within 800 m) and then EVICT tiles, ending with 1 of 3 tiles resident, because its only real lever was coverage. Measured, 3 interleaved rounds on an Intel Iris: pan **24–29 → 48–49 drawn fps, p50 26–34 → 17 ms, p95 92–94 → 33–34 ms**, frames over 50 ms 20–34 → 7–9, readback stall 30–47 → 16–18 ms, and the budget never cut (was ×0.6–0.8). `getSplatsStats().governor.thinKeep` reports the rung. Also measured and NOT adopted: thinning the full mesh in place of the lite swap (no mapping change, but 37 vs 49 fps and the same gesture-start hitch).

- **Splats: the map holds its picture while the motion-LoD swap sorts.** Showing the lite meshes changes Spark's splat mapping, and Spark keeps drawing the previous set until the new set's first depth sort lands. At the start of a gesture that previous set is the full detail (~1M splats, 90–150 ms a frame on an Intel Iris), and the sort's readback waits behind those frames: ~600 ms of 90–270 ms frames at every gesture start, the same with the GPU pre-warmed, while regenerating either set costs 1–2 ms. Now the first held tick runs Spark's update itself (generate + start the sort on an idle GPU), the map draws nothing until the lite set is sorted (≤ 200 ms), and the first frame drawn is the lite set. It only starts from an idle GPU and an idle Spark: with frames still queued from a busy rest, the readback would block the main thread behind them and no cap could cut it short (measured: one 225–360 ms freeze), so the map falls back to drawing as before. Measured, 3 interleaved rounds, gesture from rest: **worst frame 169–278 → 110–118 ms**, time in frames over 50 ms 512–615 → 296–390 ms in the first 0.7 s; worst frame of the whole pan 169–360 → 110–118 ms. `getRenderStats().swapHeld` counts held ticks.

- **Splats: motion LoD — `splats.motionLod` (default on).** With a lite pyramid (`lowTierUrlTemplate`) on the `'high'` tier, every resident tile also loads its lite version (~45 % of the splats) and draws it while the camera moves, back to full detail 250 ms after it stops — a visibility flip between two resident meshes that share one modifier graph, nothing refetched. Diagnosis first: the frame cost is per splat, not per pixel (render scale 1 / 0.75 / 0.5 → the same 27–29 fps), so fewer splats in motion is the lever. Decoded tiles also wait to land until the camera settles (a landing is a ~400k-splat upload and resort). Measured, default settings, three interleaved rounds on an Intel Iris: pan **22 → 41–42 drawn fps, p50 35 → 17 ms, p95 108 → 57 ms**, sort stall 128 → 58 ms. Costs ~45 % more splat memory per tile. `&motionLod=0` in the example for A/B. Spark's own continuous LoD was tried first and rejected (slower pans, 3× slower tile builds, continuous rendering at rest) — see `docs/splats-performance.md` §6.

- **Splats: Spark's LoD worker is no longer started.** The tiles are plain `.spz` with no LoD trees — the tile pyramid is the level of detail — yet Spark's LoD driver ran on every update and posted an empty job to a dedicated worker each frame. `enableLod: false` on the overlay's `SparkRenderer`: one thread fewer, nothing visible changes.

- **Splats: basemap mesh uploads wait for the gesture to end while the lean map is on.** The `interactionTilePriority` gate (off by default) is forced on while splats show: a vector-tile upload mid-pan only competes with the splats for the GPU, and the backlog lands the moment the camera settles.

- **Splats: zoom cap 16.5 (was 17).** Measured at a 62° tilt, the near edge of the frame was ~0.47 m per screen pixel at 17 — finer than the 0.45 m surfels and the ~0.4 m satellite ground texels, so both were magnified (blurred roads and cars, surfel dots on roofs). At 16.5 it is ~0.7 m/px and nothing is magnified.

- **`performance.framePacing` (now default on with motion LoD): GPU frame pacing while splat tiles are resident.** With motion LoD's lighter frames it is a clear win — frames over 50 ms 43 → 17 per pan, sort stall 58 → 28 ms, p95 57 → 50 ms, for 3 % fewer frames drawn. The entry below records the earlier, pre-motion-LoD measurement, when it was a trade. Spark's per-sort depth readback (`getBufferSubData`) waits behind every frame queued after it, and a GPU-bound loop keeps that queue deep (90–120 ms per sort on an Intel Iris, 330 ms worst). With pacing, a new frame is only submitted while fewer than two are unfinished on the GPU (a fence per frame, polled without blocking). Measured, 4 interleaved rounds: the stall halves (108 → 51 ms) and frames over 50 ms drop by 30 %, but 7 % fewer frames are drawn and the p95 interval lengthens — a trade on that GPU, so it ships off. `getRenderStats().paced` counts held-back ticks. Also measured and NOT adopted (see `docs/splats-performance.md` §5): an 8-bit sRGB colour target (no change), gating Spark's accumulator regeneration to the sort cadence (no change), holding all submission during a readback and one frame in flight (both fewer drawn frames).

- **Splats: no render heartbeat while splat tiles are resident.** The render-on-demand loop forces a safety-net redraw every 30 ticks in case a dirty source was never wired up. With splats resident each of those redraws re-rasterises every splat from a cold GPU: measured 100–150 ms, twice a second, on a map standing perfectly still (long frames at ticks 49, 81, 141, 171, 201, 234 — the heartbeat stride). The overlay nudges `needsRender` itself for everything that changes its picture (sorts, landings, fades), so the heartbeat is skipped while it has tiles: a still map with splats now draws **0 frames in 5 s (was 9, worst 150 ms → 17 ms)**.

- **Splats: a lean map while they show — `splats.leanMap` (default on).** Every resident splat is re-rasterised on every rendered frame, so while the overlay is on the map spends the GPU on nothing else: the outline pipeline (a second full-scene render + Sobel), the cloud raymarch and the tilt-shift blur are switched off, the ambient animations (trees, grass, foam, signs) are frozen, and dynamic resolution renders the moving picture at 1× on a Retina display. All of it comes back the moment the overlay is disabled; `setCloudsEnabled` while lean records the wish for then. On the Intel Iris reference machine at an emulated 2× DPR, a pan with one 283k tile resident went from 22–23 fps / p95 117 ms to 27–37 fps / p95 50–100 ms (the remaining cost is the splats themselves — see `docs/splats-performance.md` for the matrix). `getSplatsLeanMapActive()` reports it; the example shows "lean" in the HUD and takes `&leanMap=0` for A/B.

- **`getRenderStats()`: why did the map render?** Counters since the previous call — RAF ticks, renders, and which dirty source asked for each (`needsRender`, `tileDirty`, `layersDirty`, bridges, spores, clouds, noise, heartbeat), plus renders drawn at the motion resolution. The map is render-on-demand, so on a still scene `renders` should be near zero; when it is not, the non-zero reason names the layer keeping the GPU busy. This is how the heartbeat cost above was found.

- **Splats: the governor now answers a BURST of hitches.** Measured on an integrated GPU during a pan with 1.15M splats resident: every depth re-sort stalls the main thread in a GPU→CPU readback (`getBufferSubData`) that waits for the GPU to drain — 121 ms on average, 352 ms at worst, once per sort interval, with 17 ms frames in between. 24 % of frames were over 50 ms and the budget never moved, because the EMA clamps each hitch (rightly: one hitch is a tile upload) and so never reads "over". `hitchBurst` (8) hitches inside `hitchWindowMs` (2,000) now take one ordinary step down the degradation ladder. A phone's occasional hitch (~4 per window) still only withholds growth. The stall is proportional to resident splats — 88 ms at 283k — so the budget is the right lever; the sort interval is not (fewer, longer stalls).

- **Splats: a lite pyramid for weak devices — `lowTierUrlTemplate`.** A second tile template fetched instead of `urlTemplate` on the `'low'` / `'mobile'` quality tiers. A pyramid built with fewer, larger surfels (`splatmap tiles --spacing 0.7`: ~165k splats per z16 tile against ~280k at the default 0.45 m) gives a phone or an integrated GPU whole tiles inside `lowTierMaxSplats` instead of a budget-starved window. A tier flip with a lite template configured drops the resident tiles and refills from the right pyramid; without one, nothing changes. Exported by the Studio only when set.

- **Splats: the imagery ground no longer hides the base of the walls.** Its polygon-offset bias was `-2 × zoom` (−32 at z16) so finer pyramid levels win a cross-fade; splats depth-test against that plane, and a slope-scaled offset of 32 swallowed the bottom ~32 px of every wall. Buildings looked cut off above the ground although their surfels reach z = 0. `groundDepthBias` is now relative to the coarsest resident level: zero for a lone level, `-2` per level of difference during a transition.

- **Example: a "3D Satellite" button.** Shown whenever a tile source is configured — `?splats=` as before, or a build-time default via `VITE_SPLATS_TEMPLATE` (`.env.local`), which starts OFF and is switched on with the button so the plain demo stays plain. `?splatsLite=` / `VITE_SPLATS_LITE_TEMPLATE` name the lite pyramid. See `.env.example`.

- **Splats: a prefetched tile that cannot fit is no longer fetched again every tick.** The prefetch path decoded the next level's tile ahead of a threshold and dropped it for either of two reasons — the camera left the band, or the tile was larger than the budget plus its dissolve allowance — without distinguishing them. The first is about the moment; the second is a property of the TILE, so dropping it silently meant the next idle tick fetched, decoded and discarded exactly the same tile again. Measured with a camera parked in the band and a small budget: **137 requests for one tile in 25 seconds with no user input at all**, now 0. The size verdict is recorded the way `commitTile` already records it, and the prefetch guard honours that record (it is cleared when the centre moves, so a genuine change of situation still gets a fresh attempt). Reachable on any device whose budget the FrameGovernor has scaled down.

- **`setView` rejects an options object instead of silently going to NaN.** `setView(lat, lon, zoom?)` is positional, and `setView({ lat, lon, zoom })` is the natural mistake — it projected `undefined`, parked the camera at NaN and left the map rendering nothing, with no error anywhere. It now throws a `TypeError` naming what was actually passed (`lat=an object, lon=undefined`) and pointing at `flyTo({ lat, lon, ... })` for the object form. The throw happens before any camera state changes, so a bad call leaves the map exactly as it was rather than wedging it.

- **Splats: `isCovered` asks the wanted set, not "the active level".** Internal refactor toward per-tile level selection (`docs/per-tile-lod.md`), with no behaviour change: the rule for when a resident tile may go is now phrased against `desiredTiles()` and never assumes its replacements form a contiguous range — only that they are the wanted tiles lying over that ground. The coarser/finer asymmetry is unchanged and now documented as deliberate: a coarser replacement must have LANDED (there is one tile over that ground, so a 404 would leave a hole), while finer replacements need only be SETTLED (one missing child just means no data for that patch). `windowRange` became unused and was removed.

- **A blocked worker now says so.** If the tile-decode worker cannot start — almost always a Content-Security-Policy without `worker-src` — `createHereBeDragons` used to reject with a bare `SecurityError: Refused to create a worker`, which mentions neither the map nor the policy that caused it. It now explains that no tiles can be decoded and names the directive to add (`worker-src blob:`, since the decoder is inlined as a blob). If only *some* workers fail to start, the pool keeps the ones it has and warns that decoding will be slower, rather than failing outright.

- **Splats: a failing tile is no longer retried forever** (`MAX_TILE_ATTEMPTS`, 3). A tile that 404s was already treated as absent, but one that failed to FETCH or DECODE was retried on every pass with no limit. Measured against a host returning corrupt bytes: one stationary camera produced **937 tile requests and 1878 console warnings in 16 seconds** — about 60 requests per second per client for the same handful of tiles, with the console too noisy to read. Each tile now gets three attempts and is then treated as absent, saying so once (`failed 3x, giving up`); the same scenario is now **108 requests and 220 lines**, and the counter resets whenever the overlay forgets which tiles are absent, so a server that comes back is not written off permanently. The base map was never at risk — it survives a splat host that is refusing connections, returning 500s, serving garbage or serving truncated files — but it survived them noisily.

- **First-run errors say what is wrong and where.** `createHereBeDragons` now validates its arguments before anything touches them, and failures opening the tile archive are diagnosed rather than passed through raw. Previously a wrong or cross-origin `pmtiles_url` rejected with a bare `Failed to fetch` naming neither the URL nor a cause, and a missing `center` surfaced as `Cannot read properties of undefined (reading 'lat')` from inside the camera — both send a new user looking in the wrong place on their very first run. Now: a missing container, `pmtiles_url` or `center` each say which argument is wrong and what it should be; and an archive that will not open reports the URL plus the likely cause, distinguishing a host that ignores `Range` requests (PMTiles reads the file in pieces, so `Accept-Ranges` and 206 responses are required — plain static servers often fail here), a 404, a 401/403, and CORS. CORS is only blamed when the archive is genuinely on another origin, because telling someone to add `Access-Control-Allow-Origin` to a same-origin file sends them to fix a header that was never the problem. The original error is always appended, so nothing is lost when the guess is wrong.

- **Tilt-shift keeps the labels sharp.** The miniature effect blurred the place names along with the geometry, which is a functional loss rather than a stylistic one — a map you cannot read is not a better map. Labels are now held out of the colour pass while the effect is running and drawn sharp over the blurred picture afterwards. The catch, and the reason this is worth a note: `scene.background` must be detached for that second pass, because three.js's background step sets `forceClear` whenever the background is a `Color` (which this map always sets, from the theme sky) and that clear runs **even with `renderer.autoClear` off** — leaving the whole map blanked to the sky colour with only labels on it. Street names that used to smear into invisibility are now legible, and it costs nothing measurable: 95th-percentile frame 21-22 ms with the effect on versus 21 ms with it off, two passes at tilt 62 with the budget pinned. See `docs/tilt-shift-labels.md`.

- **Governor: speculative growth answers for the tail it creates.** `budgetGrowth` (below) is granted on a quiet tail and REVOKED on a hitchy one, stepping back toward x1 with the usual regret back-off so a grant and a revoke cannot oscillate. Two things make this necessary rather than tidy. First, a pre-condition alone cannot work: the tail is quiet at the smaller budget, so the gate opens, the budget grows, and only then do the long frames appear — the growth is what causes them. Second, the frames that show it never reached the governor at all: `reportFrame` drops tile-upload and level-dissolve frames as "not draw cost", which is right for the average (reading them would ratchet the budget down at every load) but exactly wrong here, because a bigger budget means more resident tiles and therefore more uploads. Those frames are now passed to `noteHitch()` instead, which can only give back growth taken above the configured budget and can never cut below it. Measured on an emulated phone at `budgetGrowth: 2`, two passes: before, it grew to x2 / 5 tiles with a worst frame of 182-190 ms and 2-9 % janky frames while the median sat unchanged at 17 ms and the EMA never came near target — no other rule here would ever have given it back; after, it tries the growth, sees its own tail, and settles at x1 / 2 tiles, p95 20 ms, worst 23-33 ms, **0 % janky frames**. The same build keeps the full growth on the desktop (9 tiles, 2.29M splats). One option, opposite outcomes, decided by evidence rather than by a hardcoded tier rule.

- **Splats: the governor can grow the budget, not only cut it** (`budgetGrowth`, default `1` = off, cap 4). A cut-only governor makes `maxSplats` a number that has to be safe on the weakest device it will ever run on, so every device above that line leaves its headroom permanently unused — on the reference machine (Intel Iris Plus) the shipping default settles at 3 tiles / 0.93M splats holding a 95th-percentile frame of 19-22 ms with the governor never once engaging. Above 1 the budget becomes a STARTING POINT and the device finds its own level, by the same evidence rule as every other raise (4 s of moving frames under 0.7 x target buys one x1.25 step; a step that has to be taken back doubles the wait). Growth is deliberately the LAST raise in the order — bias, then scale back to 1, then the distance cutoff, and only once nothing is degraded does the budget go past 1 — so it can never grow while the picture is still recovering. Measured live via `setSplatsOptions({ budgetGrowth: 2 })` with no reload, two passes: 3-5 tiles / 0.93-1.05M splats -> 10-11 tiles / 2.11-2.23M, i.e. **~2.5x the 3D ground coverage for +1 ms of 95th-percentile frame** (20-21 -> 21-22 ms), 59 fps and 0 % janky frames throughout; the honest cost is in the tail, p99 22-25 -> 26-31 ms. Setting it back to 1 takes the lent-out growth back at once. Off by default because it buys coverage with memory and bandwidth, which is a product call rather than a safe one; `getSplatsStats().governor.maxScale` reports the ceiling. The cost depends on the camera, so judge it on more than one: the +1 ms above is at tilt 45, while at tilt 58 the same growth costs p95 20 -> 26 ms with 1-3 % janky frames, and on a phone it is rejected outright by the rule above. Measured heap cost on the reference machine, 3 tiles -> 9-10: +25-35 MB, with the `.spz` fetch count going 3 -> 10-11.

- **Splats: the distance cutoff fades** (`splatFadeMs`, default 350 ms). A tile crossing `splatMaxDistance` now eases its splats out over the imagery instead of blinking, which matters because the FrameGovernor moves that cutoff on its own mid-pan. The fade multiplies into the existing per-tile level-fade path and applies to the SPLATS only — the imagery ground plane keeps drawing throughout, so the picture never gains a hole. A fully faded tile is then hidden outright, so it still costs nothing: cutoff 800 m at tilt 70 keeps its 2.69M → 1.18M splat reduction and 95th-percentile frame 35 ms → 21 ms.
- **Fixed:** the culling and distance options (`frustumCull`, `visibleFirst`, `splatMaxDistance`, `lowTierSplatMaxDistance`, `splatFadeMs`) were only read at construction, so `setSplatsOptions()` silently ignored them. They now apply live.
- **Fixed:** the same constructor-only bug in the level-selection options — `levelSelection`, `resolutionMargin`, `resolutionTiltAware` and `lodRenderScale`. These only decide which level the next tick asks for (a level change is already a supported transition), and Spark exposes `lodRenderScale` on the live renderer, so none of them needed a rebuild; they were simply never re-read. This one also invalidated a measurement: switching to `'resolution'` mode at runtime appeared to do nothing, which was reported as the two rules agreeing at that zoom. Re-measured after the fix, at camera zoom 14.6 / tilt 50 the modes are two levels apart — `'bias'` z16 / 2.15M splats, `'resolution'` at the default margin z14 / 0.67M. A guard test now diffs the `this.x = o.y` assignments in the constructor against `applyOptions` and fails on any option set in one but not the other, so a future option cannot be added to only half the path.

- **Governor: distance before coverage.** The `FrameGovernor` now walks a `splatMaxDistance` ladder (2000 → 1200 → 800 m) BEFORE it shrinks the tile budget, and gives it back last. Pulling distant relief in keeps the whole satellite picture (the imagery ground plane still draws out there); shrinking the budget evicts whole tiles. Observed under 4x CPU throttling with a 20 ms target: the cutoff tightened 2000 → 1200 while the budget stayed at 1.00, and only then did the scale start falling. `getSplatsStats().governor` reports `splatMaxDistance`.
- **`lowTierSplatMaxDistance`** (default `1200`): a cutoff floor on the `'low'` / `'mobile'` tiers even when the governor is idle, mirroring `lowTierMaxSplats`. Phones pay most for distant relief and show it on the fewest pixels. `0` opts out.

- **Splats: `splatMaxDistance`** (default `0` = off). Beyond this distance in scene metres a tile's splats stop drawing while its imagery ground plane keeps going — both come from the same photograph, and past a few hundred metres an individual splat is under a pixel, so what is given up is distant RELIEF, not detail. Measured at camera zoom 16.4 / tilt 70 over two paired runs, cutoff 800 m: drawn splats 2.69M → 1.18M (−56 %), 95th-percentile frame 30-34 ms → 20 ms, worst frame 35-38 ms → 21-22 ms. Side-by-side captures differ only in a thin band of distant treeline at the horizon. Left off by default because it trades appearance for speed; the obvious place to enable it is the low/mobile tiers.

- **Splats: `visibleFirst` split out of `frustumCull`.** The two are separate concerns — one decides what is DRAWN, the other what is LOADED first — and sharing an option made A/B measurements conflate them. Both still default `true`.

- **Splats: visible tiles load first.** The screen-relevance ranking scores a tile by a point, so at high tilt it could start fetches for tiles entirely outside the view before ones inside it. The ranked window is now partitioned by an actual frustum test (box inflated half a tile so a tile about to scroll in is not starved), keeping relative order within each group. This affects load ORDER only: off-screen tiles still fill any budget left over, which is useful prefetch now that `frustumCull` stops them costing frame time.

- **Splats: frustum culling of resident tiles** (`frustumCull`, default `true`). Spark draws every splat of every mesh in the scene and a `SplatMesh` carries no bounding volume for three.js to cull on, so an off-screen tile cost exactly as much as an on-screen one. Each resident tile's column is now tested against the camera frustum once per frame and hidden when it falls outside. Measured at camera zoom 16.4 / tilt 70 with 17 resident tiles: 6 hidden, drawn splats 3.92M → 2.69M, 95th-percentile frame **58 ms → 32 ms** and worst frame 83 ms → 36 ms. At moderate tilt it culls nothing (the relevance-ranked window is already on screen), so it is a no-op there rather than a regression.

- **Splats: `lodRenderScale` exposed** (default 1, Spark's own). Sets the minimum on-screen splat size Spark's LoD tree will pick. Measured on the reference hardware at 2.4-2.7M resident splats, raising it to 2 or 4 gave no reproducible frame-time change — Spark's LoD tree appears to serve its paged/streaming path rather than whole-`.spz` meshes — so the default is unchanged. Exposed for fill-rate-bound devices, where it may help.

- **Splats: tilt-aware resolution matching.** `resolutionTiltAware` (default `true`, `'resolution'` mode only) judges the level from the resolution at the NEAR edge of a tilted view rather than at the camera target, so a pitched-over camera keeps its foreground crisp. The raw near-edge factor is softened (square root) on purpose: one level serves the whole window, and since levels step by 2x, sizing for the near edge alone bought a full level — measured, 4x the splats for a quarter of the satellite coverage. The blended value only shifts the level near a threshold or at high tilt. Per-TILE level selection (near tiles finer, far tiles coarser) is the real fix for the near/far conflict and is not implemented.

- **Splats: resolution-matched level selection (opt-in).** New `levelSelection: 'bias' | 'resolution'` (default `'bias'`, unchanged behaviour) and `resolutionMargin` (default 0.5 = 2x oversampled). `'resolution'` picks the coarsest pyramid level whose imagery still out-resolves the screen, instead of keying off camera zoom. Measured at 1280x800, camera zoom 14.6 (screen 5.16 m/px): `'bias'` loads level 16 — 5 tiles, 1.39M splats, 1.25 km² of satellite — while `'resolution'` loads level 14 — 9 tiles, 0.67M splats, 36.0 km². Same picture, **29x the ground for half the splats**; at camera 15.5 it is 7.2x the ground for the same splats. At the zoom cap both rules pick the finest level, so maximum-zoom sharpness is identical. `lodBias` is deliberately ignored in resolution mode (it biases the camera-zoom rule; applying both would cancel out) — halve `resolutionMargin` for one level finer. Known trade: the margin is evaluated at the camera target, so under strong tilt the near field is softer than `'bias'`; a smaller margin trades that back. Demo: `&levelSelection=resolution&resolutionMargin=`.

- **Motion vocabulary + global reduced motion.** New `src/core/motion.ts` exports one duration scale (`DURATION.quick/base/slow/deliberate`), a set of easing curves (ease-out by default for entrances — a symmetric curve spends its first third barely moving, which reads as lag), a frame-rate-independent `approach()` for values that chase a moving target, and `prefersReducedMotion()`. The map now caches that preference, keeps it live via the media query, and shares it with every eased effect: tilt-shift strength, the neutral-grade fade, the splat overlay, and the basemap tile reveal (which keeps its rounded-union SHAPE but drops the grow animation). With reduced motion on, effects jump to their end state rather than merely running faster.

- **Splats: the first overlay toggle no longer hitches.** Spark compiles a `dyno` graph's GLSL the first time a mesh renders with it attached, so the user's first toggle paid it mid-animation — measured on an Intel Iris: 186 ms for the first reveal and 76 ms for the first hide, against 19-42 ms for every later toggle. The ripple modifier is now compiled during the initial tile load instead (attached to one resident tile for a single frame with the front fully open, which the graph resolves to scale 1 / opacity 1 — a visual no-op — then detached). First toggle is now 46 ms / 19 ms, matching the steady state. New `prewarmShaders` dep (default on).
- **Demo:** `&underlay=0` disables the low-res underlay, for performance experiments.

- **Tilt-shift "miniature" look.** New `tiltShift` option and `setTiltShift(on | settings)` / `getTiltShift()` / `getTiltShiftSettings()`: a sharp band across the point the camera looks at with blur growing above and below it (two separable variable-radius passes), plus a saturated model-photography grade applied in gamma space. The strength eases in and out (~450 ms, reversible mid-way) and the pass is skipped entirely at strength 0, so it is free while off; its two render targets are allocated lazily. Runs on the `'high'` quality tier only (the request is remembered if the tier rises). Studio: "Tilt-shift (miniature)" with Blur / Focus band / Saturation; exported as `tiltShift: true | {…}`. Demo: `&tiltShift=1`. Known limitation: labels inside the blurred regions blur with the scene.

- **Splats: WebP imagery grounds, hi-res on capable screens.** When `imageryTemplate` is derived from `urlTemplate`, the layer now tries `{y}.webp` first and falls back to `{y}.png` (WebP grounds are ~9× smaller at the same size — 235 KB vs 2.2 MB per tile in the reference set). On the high tier with `devicePixelRatio ≥ 1.5`, tiles of the finest level try `{y}@2x.webp` (2048 px) first. A candidate that fails three times before ever succeeding is dropped, so PNG-only tile sets don't pay a 404 per tile. An explicit `imageryTemplate` is used as given.

- **Splats: cross-dissolve between pyramid levels.** A level change is a change of detail in place, so it no longer uses the grow-from-centre animation: the incoming tile appears at its full shape and dissolves in over `levelFadeMs` (450 ms) while the outgoing tile dissolves out, reversible mid-way; the vector cut-out uses the union of both levels during the fade so the basemap never flashes through. `transitionOvershoot` (0.35 × `maxSplats`) lets the old level fade instead of being evicted instantly, the frame governor ignores dissolve frames, and `prefetchBand` (0.2) fetches the next level's centre tile before the boundary is crossed. Studio: "Level fade" slider.

- **Splats: tiles load centred on the camera target.** Two ranking flaws made the satellite patch appear off-centre and jump while panning: the tile window was pushed forward along the view direction by up to ~1.5 tiles (now capped to `(radius − 1)` tiles, i.e. none for the default 3×3 window), and tiles were scored by where their CENTRE lands on screen, which perspective biases toward the row ahead (now scored by the tile's point nearest the target, so the tile under the crosshair always ranks first).

- **Splats: hybrid map — `hideBasemap: 'covered'` is the new default.** Enabling the overlay no longer hides the whole vector basemap at once: the basemap stays everywhere **except under satellite tiles that have landed** — "remove the 3D houses when the satellite loads". The overlay reports its rounded union (every resident tile of every resident level, with the very growth / neighbour values its own GPU mask uses, and the ripple front) to the tile-reveal `CoverageField`, which bakes it into a **second channel** of the coverage texture (now RG8: R = tile reveal as before, G = satellite cut-out, same signed-distance encoding, stored as the ramp coordinate `s / 2·feather`; 512² while a cut-out is reserved). The shared shader chunk reads both channels with one fetch and `hbdCoverage()` returns `reveal · (1 − cut)` — the exact complement of the imagery's alpha, so the feathered satellite rim and the dithered vector cut meet with no gap and no doubly-covered band. Buildings, trees, grass, signs, cars, bridges, roads, water and foam are cut; **labels stay on top** by default (new `keepLabels: true`, through a separate `hbdCoverageLabel()` entry point; `false` cuts them too); buildings under the satellite are not hover- / click-able (`coverageAt` includes the cut, new `CoverageField.cutoutAt`); works with `tileReveal: false`. G is re-baked only when the pushed values change or the window moves (bounding box only, R untouched), in the same frame the overlay reports them. `hideBasemap: true` keeps the old global hide, `false` never hides. `getSplatsStats()` gains `basemapCovered`. **Behaviour change** for existing embeds that relied on the implicit default: pass `hideBasemap: true` for the old look.
- **Splats: `lodBias` default `0` → `1.5`, `lowTierLodBias` `-1` → `0.5`.** Tiles run one level finer than the camera zoom and switch half a zoom early (z16 from camera zoom 14.5): a smaller, sharper patch, with the vector map carrying the rest of the view. The low tiers stay one level coarser than `'high'`. `minZoom` (13) and the ±0.15 hysteresis are unchanged; the Studio's bias sliders now run −3 … +3. Pass `lodBias: 0, lowTierLodBias: -1` for the old levels.
- **Splats: frame-time governor (`governor: true`, `targetFrameMs: 33`).** Splat cost is linear in the resident splats (≈ 80 ms per million on an Intel Iris; `maxStdDev`, viewport size and sort spacing measurably do nothing there), so while the picture moves the governor tracks a smoothed frame time and, over target, scales the budget in effect down proportionally (floor ×0.25, the least relevant tiles shrink out of the union, nothing more is admitted), then — still over on the floor — steps the `lodBias` in effect down by 0.5 (at most −1). Recovery needs 4 s of moving frames under 0.7 × target per step, bias first, and a raise that has to be taken back doubles the next wait (≤ 60 s): it does not oscillate. Frames around a tile / imagery upload and idle frames are ignored; a quality-tier change or rebuild resets it. Pure logic in `splats/governor.ts` (`FrameGovernor`, exported); state in `getSplatsStats().governor` and the Studio stats line. Measured on an Intel Iris MacBook Pro, 1280×800, quality `'high'`, default budget: orbit mean 86 → 50 ms (p50 100 → 33), zoom sweep 99 → 44 ms, ripple toggle 30 → 21 ms, and `'auto'` no longer falls back to `'low'`.
- **Splats: the budget is spent where the camera looks.** The tile window is ranked by screen-space relevance (`tileScreenRelevance`: squared screen distance of the tile centre's projection from the screen centre, tile extent allowed for; off-screen / behind-camera tiles last) instead of grid distance from the centre *tile*: top-down that is ground distance from the true view centre (a four-tile budget is the 2×2 block around it, not a plus), tilted it prefers ground ahead of the target and drops the row under the camera; the window is centred half the camera's ground offset ahead (`viewFocus`). Budget evictions use the same score with 1.5× hysteresis so an orbit doesn't swap tiles back and forth; skipped-as-over-budget tiles are reconsidered after a 20° turn / 10° tilt / 0.5 zoom.
- **Idle cost: ambient layers are throttled while splats are resident.** With the basemap no longer hidden, the always-dirty `trees` / `grass` / `waves` animations would re-rasterise every resident splat each frame (46 ms frames back to back on an idle map). They now tick at ≤ 15 fps, claim at most a quarter of the GPU (interval ≥ 4 × measured frame cost) and freeze past a 150 ms interval (`LayerRegistry.setThrottle`); lifted when the last splat tile leaves. An idle hybrid map renders only the heartbeat frame.
- **Splats: neutral grade is eased, and follows the view centre in `'covered'` mode.** The grade is a full-screen post-process and cannot follow the satellite's outline, so it now eases over 400 ms (saturation, shine, paper grain) instead of snapping, and with `hideBasemap: 'covered'` it engages while the view centre is over landed satellite (with hysteresis on the rim) and releases when the camera pans off it. Also fixes a theme switch under the overlay restoring the theme's paper grain.
- **Studio / export.** "3D Satellite" gains a Basemap mode (Cut out / Hide / Keep), "Labels on top", "Frame governor" + target frame time, and the governor state in the stats line. `hideBasemap`, `keepLabels`, `governor`, `targetFrameMs` are live options, diffed, exported with defaults elided and reset by an import that leaves them out. Demo: `&hideBasemap=1|0`, `&keepLabels=0`, `&governor=0`, `&targetFrameMs=`.

- **Splats: tile pyramid (multi-level LOD) + camera zoom cap.** The overlay no longer requests one fixed zoom. New options `minTileZoom` (13) / `maxTileZoom` (16) bound a tile pyramid (z16 full detail; each coarser level = four children merged and thinned back to the same per-tile splat budget, each tile in the frame of its own zoom), and the level is picked from the camera: `tileZ = clamp(floor(cameraZoom + lodBias), minTileZoom, maxTileZoom)` with ±0.15 hysteresis (pure `selectTileZoom()` in the new `splats/lod.ts`, exported). The window stays `radius` tiles of the ACTIVE level, so tiles on screen and resident splats stay roughly constant across zooms (measured: 3–4 tiles / 0.93–1.20M splats and the same frame time at z16, z15, z14, z13). `lodBias` (0) shifts the level; `lowTierLodBias` (−1) is used on the `'low'` / `'mobile'` tiers. `minZoom` default drops **15 → 13** so the overlay shows further out. **Level transitions** are graceful: the new level loads nearest-first while the old level's resident tiles stay until the new tile(s) over them have landed and grown (zoom-out: the ancestor; zoom-in: every descendant in the new window, the periphery once the window is settled), then shrink out with the union leave animation; the rounded union is per level; coplanar imagery grounds are separated by a per-level polygon offset (finer wins); `maxSplats` counts both levels and evicts old-level tiles first, at landing time; zooming back mid-transition regrows instead of refetching; a level whose whole window 404s falls back to the next finer (then coarser) level, so z16-only tile sets keep working. **`maxCameraZoom`** (17): while the overlay is enabled the camera's max zoom is capped (new `MapCameraController.setMaxZoomCap()`, layered over `setZoomRange` and the floor-badge `suspendLimits`; a camera already closer is eased out over 600 ms) and the previous limit is restored on disable. All five options apply **live** (bounds changes re-evaluate the level — no rebuild), round-trip through `exportSplatsOptions` / `splatsReplacePatch`, and have Studio sliders; the Studio stats line and the example HUD show the active level (`z15 · 4 tiles`). `getSplatsStats()` gains `tileZoom`. **Deprecated:** `zoomLevel` is now an alias that pins both bounds (no longer a rebuild key, never exported). Tests: level selection + hysteresis, transition bookkeeping, budget preference, per-level union, transforms at z13–z16 vs `Projection`, camera cap set / ease / restore, options diff / export.

- **Splats: neutral grade.** While the overlay holds the basemap hidden, the post chain runs at saturation 1.0 (themes default to a 1.5x vibrance boost, applied in the outline pass or, on the low tiers, the final pass), with the shine highlight and paper grain off, so captured imagery and splats keep their authored colours. Demo: `&tileReveal=0`, `&revealGrowMs=`, `&revealFeather=`, `&revealRise=1`.
- **Gaussian-splat tile overlay (`splats` option).** Set `splats.urlTemplate` (`{z}/{x}/{y}.spz` or `.ply`) to stream pre-tiled 3D Gaussian splats — the SplatMap tiler's output, authored per z16 tile in a SW-corner / east / north / up Web-Mercator-metre frame — over the vector basemap. Rendered with [Spark](https://sparkjs.dev) (`@sparkjsdev/spark`), added as an **optional** peer dependency and reached only through a lazy dynamic `import()` when the option is present, so existing maps never load it. A new self-contained `SplatsLayer` mirrors the parcels overlay's tile-window loop (fixed authored zoom, square window around the camera target, nearest-first, capped concurrency, eviction, everything dropped below `minZoom` or on disable). Each tile is placed at its SW corner, rotated −π/2 about X (z-up → Y-up) and scaled by `cos(originLat)`; the pure `splatTileTransform()` helper is exported and unit-tested against `Projection`, and the placement was verified in-browser against the vector footprints (splat houses sit on the extruded buildings, not mirrored or offset). Options: `enabled`, `minZoom` (15), `zoomLevel` (16), `radius` (1), `maxInFlight` (1), `maxSplats` (1.2M), `lowTierMaxSplats` (400k), `maxStdDev` (√5), `sortIntervalMs` (100), `imageryTemplate`, `hideBasemap` (true), `clock`. Instance API: `setSplatsEnabled(on, opts?)`, `getSplatsEnabled()`, `getSplatsStats()` (`{ tiles, splats, maxSplats, reveal, basemapHidden }`). On the `'mobile'` / `'low'` quality tiers it runs under the smaller `lowTierMaxSplats` budget (see Performance below). Splat objects live on a dedicated three layer (8) that the Composer excludes from the outline normal pass.
- **Satellite ground under splat tiles.** Each loaded splat tile gets a textured ground plane from `{z}/{x}/{y}.png` (`imageryTemplate` overrides; `null` skips it) — sRGB, mipmaps + max anisotropy, 5 cm above the vector ground, fog-aware, on the splat camera layer. While ≥ 1 splat tile is showing the vector `buildings`, `roads`, `landuse`, `water`, `waves`, `trees`, `grass` and `labels` layers are hidden (`hideBasemap`, default `true`) through a new **`TileManager.setLayerHidden()`** per-layer mask that is orthogonal to `setLayerEnabled()` — decoding continues, the caller's enabled state is preserved, tiles built while hidden come up hidden, and everything is restored on disable / last-tile eviction. `SPLATS_HIDDEN_BASEMAP_LAYERS` exports the list.
- **Ripple reveal.** `setSplatsEnabled(true | false, { reveal: 'ripple', origin?, durationMs?: 1800, speedMps?: 250 })` animates the overlay in (or out) as an expanding (collapsing) circular front from `origin` (default: the view centre): splats inside the front grow 0 → 1 with a back-eased overshoot and a ±10 % sine ring riding the front, splats beyond it are collapsed (scale 0 / opacity 0), and the imagery ground fades in under the same front with a bright wave. Implemented as a per-splat GPU modifier — a Spark `SplatMesh.worldModifier` built with the `dyno` shader graph (uniforms: origin, front radius, ring width, time) — plus a small `ShaderMaterial` on the ground, driven by the map's RAF loop through `needsRender`; tiles that land mid-ripple join the current front, disable ripples inward and then unloads, and re-enabling while already on replays the reveal. The pure front / scale / opacity maths lives in `splats/ripple.ts` (exported, unit-tested); the animation clock is injectable (`SplatsConfig.clock`).
- **Splats: rounded union of the loaded tiles (`splats.roundedUnion`, default on).** Tiles no longer appear as hard squares: the visible region is the morphological opening of the union of resident tile squares by a half-tile disc — one tile is a circle, two edge-adjacent tiles a pill with the shared side fully joined, a complete 2×2 block a rounded square; outer corners always round, interior joins seamless. New pure module `splats/roundedUnion.ts` (exported; unit-tested, including against a brute-force opening and for seam symmetry — tile A at `u = 1` ≡ tile B at `u = 0`): per tile, in normalised local coords, the signed value is `r·g − d` with `d` the distance to the tile's centre, to the weight-scaled segments toward its E/W/N/S neighbours and to the weight-scaled boxes toward its complete diagonal blocks (block weight = min of its pairings), and the mask is a smoothstep `2 × feather` wide lying inside the outline. One GLSL twin (`ROUNDED_UNION_GLSL`) is compiled into both consumers and driven by the same per-tile uniform vectors: a per-tile Spark `SplatMesh.objectModifier` (raw-GLSL `dyno.Dyno` node in the tile-local frame; scale × mask, opacity × mask — it multiplies with the ripple's `worldModifier`) and the imagery ground's fragment shader (alpha × mask, plane UVs with v north). Animated off the injectable clock: a landed tile grows from its centre over `growMs` (700 ms, ease-out); when it is ~60 % grown the joins toward it grow from both sides over the same duration (each bridge as thick as the thinner of the two tiles, so the two sides of a seam match mid-animation too); tiles that drift out of the keep zone shrink out over 300 ms before unloading, while budget / tier evictions stay immediate and leave only a timestamp "ghost" so the neighbours' joins retract instead of popping. `updateVersion()` is bumped only for tiles whose weights changed and frames are requested through `onSceneChange` only while something animates, so the mask costs nothing at rest or while orbiting. Options: `roundedUnion?: boolean | { feather?: number /* 0.03 tile */; growMs?: number /* 700 */ }`; `false` restores square tiles.
- **Demo:** `&roundedUnion=0`, `&unionGrowMs=`, `&unionFeather=`, `&splatsMinZoom=`.
- **Demo:** `?splats=<urlTemplate>` (plus `&hideBasemap=0`, `&tilt=`) on the dev page; the map is exposed as `window.map` and the splat clock as `window.__splatsSetTime(ms)`.

### Changed

- **`splats/roundedUnion.ts` moved to `core/roundedUnion.ts`** (re-exported from the old path): the maths is now shared by the splats overlay and the basemap tile reveal. New shared helpers `unionTileValues()` / `unionPairWeight()` / `unionPresenceGrowth()` (the membership → 16 mask values step, previously private to `SplatsLayer`, which now calls them) and `roundedUnionSignedPacked()` (allocation-free CPU evaluator, 4 square roots instead of 9, tested equal to `roundedUnionSigned`).
- Road / rail / surface / building materials now set `customProgramCacheKey` — three keys programs on `onBeforeCompile.toString()`, which was identical for the road, path and rail variants (and would have been for the masked / unmasked twins).

### Fixed

- **Splats: two overlapping `SplatsLayer.open()` calls no longer add two `SparkRenderer`s** (the second awaits the first import), and `dispose()` cancels Spark's pending sort timer first — left alone it fired after the render targets were freed and rejected with "No target".
- **Splats: the ripple modifier is now actually detached when a reveal ends.** Spark's `SplatMesh.worldModifier` is a setter with no getter, so the layer's "already applied?" check always read `undefined` and the end-of-ripple removal was skipped on the real mesh (harmless on screen, but every later regenerate still ran the ripple graph). The attached state is now tracked on the tile.

### Performance

- **Splats overlay: resident-splat budget, staggered landings, and an idle loop that actually idles.** Profiling the first cut on an Intel Iris Plus 645 (the `'low'` tier's reference GPU) showed the "freeze" was not decode (Spark inflates/unpacks `.spz` in its worker pool) but *residency*: the 5×5 default window pulled ~6M splats resident, and every Spark sort pass then blocked the main thread for 1–2 s inside `readRenderTargetPixelsAsync` (the depth readback waits for the GPU to drain) plus a ~24 MB ordering-texture `texSubImage2D`, while plain redraws cost ~450–550 ms each — and the redraws never stopped, because the `grass` / `waves` layers kept reporting the scene dirty every frame from underneath the overlay. Fixes: new **`maxSplats`** budget (default 1.2M) with nearest-first loading that stops at the budget and farthest-first eviction when the view moves (the centre tile always loads); defaults **`radius: 1`**, **`maxInFlight: 1`**; decoded tiles and imagery textures attach **one per frame**; Spark runs with `maxStdDev` √5, SH pinned to degree 0, and sort passes spaced by **`sortIntervalMs`** (100 ms; ≥ 250 ms on the low tiers); layers masked by `hideBasemap` (now including `waves`) stop ticking via the new `LayerRegistry.setSuspended()`, so render-on-demand idles again. The `'low'` / `'mobile'` tiers no longer disable splats: they use **`lowTierMaxSplats`** (default 400k, radius ≤ 1; `0` restores the old forced-off behaviour). `getSplatsStats()` gains `maxSplats`. Same scene after: 17 ms at rest, ~33 ms orbiting, no frame over 100 ms with one 290k-splat tile on the low tier. Demo: `&maxSplats=`, `&lowTierMaxSplats=`, `&radius=`.

## 0.9.1 — drop the fast pan stop

### Removed

- **`fastPanStop` option (and `getFastPanStop()` / `setFastPanStop()`).** It existed only to make a pan settle fast so sharp detail snapped in sooner after the coast; now that the map renders full detail throughout a gesture (dynamic resolution off, tiles building during motion), there is nothing to wait for and the snappy pan stop is no longer needed. Pan inertia reverts to the long, smooth glide it shared with zoom (a single `dampingFactor` of 0.05). The Studio `Performance` section drops its `Fast pan stop` checkbox; the other two toggles remain.

## 0.9.0 — detail-first interaction defaults

This release retunes the pan/zoom interaction model to favour **live map detail** over maximal gesture smoothness, and surfaces the whole tradeoff as three toggles in the Studio. Out of the box the map now keeps full resolution while you move, builds fresh tiles mid-gesture, and stops a pan quickly so sharp detail snaps in sooner. The smoothness-first behavior is still one option away.

### Added

- **`fastPanStop` option (default on): a pan settles in a few frames instead of ~a second.** A pan gesture coasts to a stop under inertia damping after you let go; the coast now decays fast so the camera comes to rest quickly and sharp, full-resolution detail snaps in sooner after a pan. Implemented as a per-gesture damping swap in `MapCameraController` (pan drags get a high damping factor; wheel and pinch zoom keep their long, smooth tail via touch-point counting), so zoom feel is untouched. Exposed as `getFastPanStop()` / `setFastPanStop()`. Disable for a longer glide that matches the zoom feel.
- **`interactionTilePriority` option (default off): opt-in scroll/zoom smoothness over tile loading.** The map can suspend tile-mesh construction entirely for as long as a gesture is live (drag, pinch, wheel, and the damping inertia glide that trails it), so a pan or zoom never competes with a build. Tiles keep fetching and decoding in the background, then drain a couple per frame once motion settles. Wired off MapControls `start`/`end` events plus a short post-motion settle window; the decision logic is a framework-free, unit-tested module (`src/controls/interactionGate.ts`). Exposed as `getInteractionTilePriority()` / `setInteractionTilePriority()`. **Off by default** so fresh detail streams in mid-pan/zoom; enable it to trade that for maximally glass-smooth gestures (tiles then appear a beat after you stop).
- **Studio: `Performance` section.** Three checkboxes expose the smoothness-vs-detail tradeoff and round-trip through the exported JSON: `Load tiles while moving` (inverse of `interactionTilePriority`), `Motion blur (faster)` (`dynamicResolution`), and `Fast pan stop` (`fastPanStop`).

### Changed

- **`dynamicResolution` now defaults off (was on).** The motion downscale rendered pans/zooms (and tile streaming) at a cheaper pixel ratio and snapped back to full resolution on settle — visibly softening the map in motion and popping crisp at rest. It now defaults off so the map stays at full resolution throughout; gesture smoothness is carried by the interaction gate instead, which needs no resolution drop. Enable it for fill-rate-bound devices that can't hold frame rate at full Retina mid-pan.
- **Benchmark harness (`npm run bench`) gained motion modes + jank metrics.** New `?mode=pan|orbit|fling|zoom` drives panning across new territory (the case that actually exposes scroll jank, which the in-place orbit never triggered), and the report now includes p99 / max frame time, dropped-frame count, and hitch count rather than median fps alone. `?gate=0|1` toggles the interaction gate and `?dynres=1` mirrors the real-app render path, for clean A/B runs.

### Performance

- **Bounded the tile-upload spike that caused scroll/zoom stutter.** Building a decoded tile into a mesh forces a synchronous GPU buffer upload on the *next* render, a cost the existing per-frame build-time budget can't see (it only bounds CPU build time). Building several tiles in one frame queued several large uploads into a single render, producing multi-hundred-millisecond spikes when a fresh row of tiles popped in. The apply queue now also caps the *number* of tiles built per frame, spreading uploads across frames so no single render stalls. Visual-neutral; the map fills over a few extra frames instead of one janky one.

## 0.8.0 — mobile quality tier + GPU-memory wins

### Added

- **`quality: 'mobile'` tier + auto-detection** — the most capable map a phone-class GPU (e.g. an iPhone 8, A11 / PowerVR GT7600, 2 GB shared RAM) can sustain. It keeps the full real-estate feature set — extruded 3D buildings, labels, tags/markers + clustering, the parcels overlay, comp-radius polygons, and tap-select + hover popups — and drops only the cinematic dressing a phone can't afford: the volumetric clouds, the sketch-outline pipeline, and the ambient decoration layers (trees, grass, shoreline waves, shop signs, traffic cars, drifting spores, painterly surface wash), forced off regardless of theme. It caps `pixelRatio` to 1.5, disables the z11 low-res underlay (saves 10–30 MB of GPU memory on a device with a tight WebGL budget), tightens the resident tile window, and caps tilt at 60°. Under `quality: 'auto'` (the default) phones and tablets are detected at construction — by platform, since iOS Safari redacts the GPU string — and start on `'mobile'` so a 2 GB device never spikes through the full retina chain and loses its WebGL context. A phone too weak even for this auto-downgrades to `'low'`. Exposed as an explicit `quality: 'mobile'` for forcing, and `getQualityTier()` / `setQualityTier()` now report and accept it.
- **Studio: `Mobile` quality tier control + `quality` round-trip.** The Studio's Quality section gains a third `Mobile` tier button alongside `Low` / `High`, and switching tiers now resyncs the whole panel (the mobile/low tiers flip ambient-FX and building toggles that other controls mirror). The chosen tier is written into the exported JSON `quality` field so a config round-trips its render tier; an untouched `'auto'` map deliberately omits `quality` so a phone re-detects to `'mobile'` on reload instead of inheriting a baked-in desktop tier. `setConfig()` now also accepts `quality: 'mobile'` on import.
- **Docs: completed the options reference.** The README's options table now documents every `HereBeDragonsOptions` field (previously `msaa`, `dynamicResolution`, `parcels`, `scaleBar`, `fog`, `labelHeight`, `tileSpawnDurationMs`, and `lowResUnderlay` were undocumented), grouped into Required / Camera / Theme / Atmosphere / Overlays / Performance sections, and corrects the theme list (15 themes, incl. `greyscaledark`) and a broken anchor link.

### Performance

- **Lazy-allocated the outline + cloud render targets.** The normal target, outline target, and half-res cloud target are now materialized on first use instead of eagerly in the constructor. The sketch-outline pipeline and volumetric clouds are off on every default quality tier, so most maps never needed these full-resolution HalfFloat targets at all — eager allocation was burning roughly 130 MB of GPU memory at 4K × DPR 2 (and ~10 MB on a phone) for buffers that never got drawn into. They allocate (and resize) on demand exactly like the existing noise target; no change to the rendered image. This is the single biggest memory win for the new mobile tier, and it benefits the desktop `'high'` tier just as much.
- **Dropped MSAA on the default framebuffer.** The renderer is a multi-pass pipeline — all 3D geometry is drawn into offscreen render targets and the canvas only ever receives the final full-screen FXAA blit, which has no internal primitive edges for MSAA to anti-alias. The WebGL context now requests `antialias: false`, removing a multisampled backbuffer allocation and an MSAA resolve on every presented frame. Scene anti-aliasing is unchanged (handled by FXAA and the offscreen targets' own samples), so the rendered image is pixel-identical. An explicit `antialias` option still overrides.
- **Removed redundant per-pass framebuffer clears.** `WebGLRenderer.autoClear` is now off; the Composer already issues an explicit `clear()` for every pass that needs one, so the default auto-clear was clearing each target a second time (plus a wholly redundant canvas clear before the fullscreen blit). This trims one full-target clear per pass across the whole chain. Visual-neutral.

## 0.6.1 — ship-to-clients

### Added

- **`professional` theme** — clean, neutral palette tuned for client-facing real-estate maps: soft grey buildings, calm blue water, restrained outlines, a strong professional-blue building/floor highlight (`#2563eb`) for picking out listings and comps. Every Ghibli FX field is deliberately omitted so `applyMergedPalette` resets them to off.
- **`REAL_ESTATE_TAG_PRESETS`** — seven frozen, opinionated tag styling defaults (`forSale`, `pending`, `sold`, `newListing`, `openHouse`, `comp`, `subject`) covering the standard listing states. Spread into `map.addTag` for a polished one-liner marker. Exported types: `RealEstateMarker`, `RealEstateTagPreset`.
- **`makeRadiusPolygon(lat, lon, radiusMeters, segments?)`** — geodesic-circle helper for comp radii, walkability buffers, service areas. Sub-metre accurate at city scale (spherical destination-point formula, verified by haversine round-trip in tests). Wraps the antimeridian, clamps `segments` to ≥ 3.
- **Public perf-metrics API**: `getFps()` and `getFrameMs()` so consumers can wire their own perf HUDs without depending on the demo. Joins the existing `getQualityTier`, `getPixelRatio`, `getDynamicResolution`.
- **Demo `?investor=1` flag** — wires the seeded listings to `REAL_ESTATE_TAG_PRESETS` and draws a `makeRadiusPolygon`-based comp-radius around the subject property. Combined with `?theme=professional`, one URL showcases the clean theme + tag presets + radius helper to a prospective client.
- **Hover-cursor on buildings**. The canvas cursor swaps from `grab` to `pointer` the moment a user hovers a building, signalling clickability — the property-shopping UX clients reach for. The raycast is RAF-throttled inside BuildingsManager so a fast-moving pointer can't burn dozens of raycasts per second, and it's idempotent (only touches the cursor when the hovered state actually flips) so it doesn't step on the drag `grabbing` cursor.
- **Hover building highlight**. Pairs with the cursor swap: the actually-hovered building gets a subtle warm brighten (per-fragment, gated by a new `uHoveredBuildingIndex` uniform driven by `BuildingsLayer.onBeforeRender` — same per-mesh-push pattern the click selection uses). The pointer raycast now resolves the hit triangle to its `buildingIndex` and only triggers a redraw when the hovered (mesh, index) pair actually changes, so a pointer drifting across a single building costs nothing.
- **Scale-bar overlay**. A small `100 ft / 50 m` ribbon pinned bottom-right of the map. Investors think in distances ("are these comps within walking distance?"), and every print real-estate map has one. Click to toggle units. Defaults to imperial (the primary audience is US real-estate); pass `scaleBar: { units: 'metric' }` for international maps, or `scaleBar: false` to suppress. Picked from a fixed round-number progression (1/2/5/10/25/50/100/250/500/1000 ft, then miles) so the label is always the kind of number a human reads on a printed plan. Recomputes on `viewchange` (not RAF) so an idle bar costs zero. Paired with a public `getMetersPerPixel()` on the map so consumers can wire their own distance overlays.
- **Public `getMetersPerPixel()`**. Ground meters per CSS pixel at the camera's current lat + zoom (Web Mercator scale). Powers the scale-bar internally; exposed so consumer apps can drive their own measurement UIs without duplicating projection logic.
- **`snapshot()` API**. Capture the current map view as a data URL — synchronous, no extra render-target plumbing. The trick: render and read the canvas in the same JS tick (no awaits between), which preserves the framebuffer even with the default `preserveDrawingBuffer: false` (which is much faster for the normal render loop). Pass `{ pixelRatio: 2 }` for HiDPI print/PDF exports; the override is temporary, the live render loop is undisturbed. PNG by default, JPEG / WebP supported with `mimeType` + `quality`.

### Performance / resilience

- **WebGL context-loss survival**. The canvas now `preventDefault`s `webglcontextlost` so three's `WebGLRenderer` can re-upload its textures, programs, and buffers on the matching `webglcontextrestored` event. The map nudges `needsRender` via a new `onContextRestored` callback so the next RAF repaints. Without this, a long tab background or GPU driver reset permanently killed the canvas.
- **Idle-tab pause**. The render loop drops itself entirely when `document.hidden` (zero CPU/GPU in a backgrounded tab) and re-kicks on `visibilitychange` with a fresh tick closure so the first resumed dt isn't a giant jump that snaps the camera damping. Cleanly unregistered in `destroy()`.
- **Bundle size baseline tracked** across each slice (see PR diffs). Total v0.6.0 cost: **+17.07 kB raw / +4.83 kB gzip** over v0.5.0 (711.58 → 728.65 kB raw; 183.21 → 188.04 kB gzip) for the entire client-ship set.
